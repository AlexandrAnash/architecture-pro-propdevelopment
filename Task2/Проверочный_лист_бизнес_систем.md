# Задание 2. Проверочный лист безопасности бизнес-систем

## Почему такие разделы

- **Управление доступом** — клиенты и собственники в одном Keycloak без разделения, у сотрудников два AD, клиенты видят чужое ФИО в ЛК, партнёр одной УК видит данные другой.
- **Безопасность данных** — ПДн лежат в 4 БД и целиком копируются в DWH. Это и 152-ФЗ (проверка законодательства — одна из целей аудита), и блокер для BI/ML.
- **Защита инфраструктуры** — сейчас только firewall на периметре, плюс гибрид с арендованным облаком, куда команды сами берут ресурсы под тесты.
- **Управление инцидентами** — у конкурента была утечка, руководство прямо про это спрашивает. Без логов не найти и причину ошибки с чужим ФИО.
- **Специфические аспекты** — то, что не легло в разделы выше: API партнёров, несколько точек регистрации, ИБ не получает все изменения.

## Проверочный лист

| № | Вопрос | Да/нет | Комментарий |
|---|---|---|---|
| **I. Управление доступом** | | | |
| 1 | Используются ли системы аутентификации пользователей для доступа к системам? | да | клиенты и собственники — auth-service-1 (Keycloak), сотрудники — AD. Но клиенты и собственники в одном Keycloak "для покупателей" без разделения |
| 2 | Ведётся ли единый реестр учётных записей? | нет | Keycloak + два AD (финансы и бизнес-системы) |
| 3 | Используется ли многофакторная аутентификация (MFA) для доступа к критическим системам и сервисам? | нет данных | |
| 4 | Реализован ли принцип минимальных привилегий при назначении ролей и прав доступа? | нет | в хранилище данных ограничений доступа нет, партнёр одной УК видит данные другой |
| 5 | Используются ли механизмы контроля доступа на основе атрибутов? | нет | нужно для партнёров: доступ только к своим ЖК |
| 6 | Проводится ли аудит и пересмотр учётных записей с повышенными привилегиями на регулярной основе? | нет | после смены руководителей передача информации развалилась |

| **II. Безопасность данных** | | | |
| 1 | Ведётся ли учёт персональных данных? | нет | ПДн в разных БД и целиком в DWH |
| 2 | Используется ли шифрование на уровне БД, файловой системы и при передаче данных по сети? | частично | СМЭВ требует шифрования и подписи, по остальному нет данных |
| 3 | Проводится ли регулярное резервное копирование данных? | да | для всех БД на нужную глубину. Защищены ли копии — нет данных |
| 4 | Выполняется ли регулярное тестирование восстановления из резервных копий? | нет данных | |
| 5 | Применяются ли средства анонимизации данных? | нет | в DWH по CDC идут сырые ПДн |

| 1 | Используется ли межсетевой экран для ограничения трафика? | да | на входе для клиентов и собственников |
| 2 | Реализована ли сегментация сети и фильтрация трафика между сегментами? | нет данных | на схеме внутри все ходят ко всем |
| 3 | Проводятся ли сканирования облачных инфраструктур на соответствие рекомендациям безопасности? | нет данных | команды сами берут облако под тесты. Есть ли там прод-данные — неизвестно |
| **IV. Управление инцидентами** | | | |
| 1 | Используется ли SIEM для анализа событий и аномалий? | нет данных | |
| 2 | Разработан ли план реагирования на инциденты? | нет данных | нужен в т.ч. для уведомления РКН об утечке за 24 часа по 152-ФЗ |
| 3 | Как часто проводятся аудиты безопасности? | нет | комплексный аудит только готовится |
| **V. Специфические аспекты** | | | |
| 1 | Регистрация клиента идёт через одну точку? | нет | витрина, CRM и Keycloak регистрируют независимо |
| 2 | Есть единые политики безопасности для API партнёров? | нет | каждая команда интегрируется как хочет, контроля передаваемых данных нет |
| 3 | В контрактах API партнёров только необходимые данные? | нет | контракты явно отдают ПДн |
| 4 | ИБ согласует изменения архитектуры и интеграций? | нет | часть решений до специалиста не доходит, специалист один на всю компанию |

## Что делать в первую очередь

1. Проверка владельца данных на бэкенде (V.2) — это уже сейчас ведёт к показу чужих данных.
2. Изоляция партнёров УК и единые политики для API (I.4, I.5, V.3, V.4).
3. Анонимизация ПДн в DWH и роли в хранилище (II.7, I.4) — без этого BI/ML делать нельзя.
4. Обязательное согласование изменений с ИБ (V.5).
