# Задание 3. Требования к внешней интеграции "Умный дом"

Диаграммы:

- контейнеры — [C4_container_умный_дом.drawio](C4_container_умный_дом.drawio)

## Что меняется в ландшафте

| Контейнер | Что | Зачем |
|---|---|---|
| smart-home-app + smart-home-db | НОВЫЙ | Права доступа к двери/шлагбауму, гостевые пропуска, номера авто, согласия на биометрию. Адаптер к API партнёра — мобильное приложение с партнёром напрямую не работает (кроме видео). Сам отправляет push |
| API Gateway | НОВЫЙ | Единая точка входа для мобильного приложения и webhook'ов партнёра. Сейчас мобилка ходит в tenant-core-app и CRM напрямую. Потом сюда же можно перевести интеграции с УК — проблема "API партнёров без единых политик" |
| auth-service-1 (Keycloak) | ИЗМЕНЁН | Сейчас собственники входят через тот же сервис, что и покупатели, без разделения. Делаем отдельный realm `owners`, партнёр регистрируется как OAuth2-клиент |
| Витрина сервисов для собственников | ИЗМЕНЁН | Раздел "Умный дом" |
| CRM собственников | без изменений | Публикует смену собственника в Kafka, smart-home-app по ней отзывает доступ |

## 1. Требования к безопасности

| № | Требование | Комментарий |
|---|---|---|
| S1 | Весь трафик с партнёром — TLS 1.2+ и mTLS | Сертификаты партнёра выпускаем/проверяем мы, ротация раз в год |
| S2 | Партнёр получает только минимум данных: внутренний id жильца, id подъезда/шлагбаума, номер авто, фото лица (только при согласии). ФИО, телефон, адрес не передаём | Проблема из аудита — контракты API отдают лишние ПДн |
| S3 | Отдельное письменное согласие на обработку биометрии. Без согласия — только открытие по звонку и из приложения | 152-ФЗ ст. 11. Отзыв согласия → удаление шаблона у партнёра в течение 3 рабочих дней |
| S4 | Биометрические шаблоны не хранятся в PropDevelopment | Фото после передачи партнёру не сохраняется |
| S5 | Обработка ПДн и хранение данных у партнёра — на территории РФ | 152-ФЗ, локализация |


## 2. Протоколы аутентификации и авторизации

| Кто → куда | Протокол | Детали |
|---|---|---|
| Мобильное приложение → API Gateway | Bearer JWT | Gateway проверяет подпись по JWKS, `aud`, срок. В токене `sub`, роли. Id квартиры из токена не берём — смотрим в CRM |
| smart-home-app → платформа партнёра | OAuth2 Client Credentials + mTLS | Scope по функциям: `access.*`, `door.*` |
| Платформа партнёра → PropDevelopment (webhook) | mTLS + HMAC подпись | Приходит только на `/partner/smart-home/*` на Gateway |
| Авторизация внутри smart-home-app | RBAC + ABAC | Роли: собственник, член семьи (добавлен собственником), гость (временный пропуск), сотрудник УК. Атрибуты: квартира, подъезд, ЖК |

## 3. Взаимодействие систем

### Регистрация лица
1. Собственник в приложении принимает согласие на биометрию.
2. Приложение → API Gateway → smart-home-app: фото + id подъездов.
3. smart-home-app проверяет в CRM, что пользователь собственник/жилец этих подъездов.
4. smart-home-app → партнёр: `POST /faces` (фото, внутренний id жильца, список точек доступа). Ответ — `faceId`.
5. Сохраняем `faceId` и согласие в smart-home-db, фото удаляем.

### Звонок в домофон
1. Гость звонит → партнер → webhook 
2. smart-home-app находит жильцов квартиры → push.
3. Приложение запрашивает у smart-home-app ссылку на видео → smart-home-app берёт у партнёра одноразовую ссылку → приложение открывает видео напрямую у партнёра.
4. "Открыть" → smart-home-app → партнёр `POST /doors/{id}/open`.
